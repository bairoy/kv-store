kv-store: a live, replicated key-value store

Four real server processes running Raft consensus, partitioned into 8 shards with 3 replicas each. This page talks to the cluster through a small gateway. Everything you do here is real.

Cluster

L leader   F follower   C candidate   x server down   - not a replica. Each partition has three replicas and exactly one leader.

Write and read a key

Writes go to the key's partition leader, are replicated to a majority, then acknowledged.

Exactly-once writes

A reply gets lost, so the client retries. With a request id the retry is recognised and not applied twice; a naive client that treats the retry as a new request counts twice.

Increments a shared counter.

Atomic transaction across partitions

Two keys on different partitions are written together with two-phase commit, where every step is itself a Raft entry.







  
Break it

  
Crash a server with kill -9. Watch leaders move in the table above while reads and writes keep working. It restarts by itself after a few seconds and catches up from its peers.

  

  
    

    


    
  
    How it works
    
  
      
    
    • Storage: an LSM tree (write-ahead log, memtable, SSTables with bloom filters, compaction).
      • 
    
    • Consensus: Raft per partition: elections, log replication, snapshots, linearizable reads.
      • 
    
    • Sharding: consistent hashing places 8 fixed partitions on servers; a routing table with epochs keeps everyone in agreement; partitions move online through Raft membership changes.
      • 
    
    • Transactions: two-phase commit across partitions, with the decision stored in a Raft log so a crashed coordinator cannot block anyone.
      • 
    
    • Reliability: request ids make retries exactly-once; overload answers BUSY before anything is written; a chaos tester kills real processes and checks the guarantees.
      • 
  
    
  
    This demo is rate limited and keeps data in memory-sized, throw-away storage.
